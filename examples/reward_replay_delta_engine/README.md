# Reward Replay Delta Engine

Reward logic changes constantly during RLHF, RLAIF, RFT, GRPO, and DPO work. Replaying every stored trajectory through parsing, judging, scoring, catalog updates, and training export is expensive; letting stale labels leak into training is worse.

This example treats reward artifacts as a CocoIndex-maintained materialized view: change one trajectory, prompt, or Python reward function and replay only the work whose dependencies actually changed.

## What You Will See

- Full backfill computes every parser, feature, simulated LLM judge, and reward stage.
- A no-op rerun records zero stage calls; the artifact graph is already fresh.
- Adding one trajectory runs one parser/features/judge/reward path, not the whole dataset.
- Changing the judge prompt reruns judge and reward stages while parser/features stay cached.
- Changing Python reward code reruns reward decisions only; judge calls stay cached.
- Quarantining a trajectory updates its catalog row and deletes its owned training-row JSONL.

With the checked-in seed set, the full scenario records 14 actual simulated judge calls versus 40 calls for naive replay. The Python reward-code step is the punchline: 0 parser calls, 0 judge calls, and 7 reward calls.

The dashboard generated by `run-demo` puts those measured counts in the hero metrics, per-run timeline, delta matrix, prompt/code provenance panel, and training-row sample.

## Outputs

The pipeline declaratively maintains the artifact mix an RL data/control-plane usually needs:

- `output/reward_catalog.sqlite` - SQLite reward rows and `reward_diffs`
- `output/training.jsonl` - consolidated training export
- `output/training_rows/` - one owned JSONL file per included training row
- `output/reward_diff.md` - pass/fail diff report
- `output/manifest.json` - active reward, baseline, judge-prompt, and row counts

`run-demo` also writes execution telemetry used to substantiate the dashboard:

- `output/verifier_calls.jsonl` - simulated LLM judge calls with prompt hashes
- `output/stage_calls.jsonl` - measured memoized-stage executions
- `output/demo_runs.json` and `output/dashboard.html` - the captured six-run scenario

The telemetry is evidence about what executed, not declarative target state. Reward rows and training rows persist the judge-prompt hash as durable provenance.

Training rows contain an OpenAI-style `messages` field plus reward, label, tool-call, and provenance metadata, so they can be filtered or adapted for OpenAI fine-tuning, TRL `SFTTrainer` / `DPOTrainer`, or downstream reward-model evaluation jobs.

## Prerequisites

Run from this repository with `uv` available. The example installs the published CocoIndex version declared in `pyproject.toml`; no local Rust build is required.

```bash
cd examples/reward_replay_delta_engine
uv run python main.py run-demo
```

This writes `output/dashboard.html` and `output/demo_runs.json`, then restores the seed inputs and baseline outputs so the working example is internally consistent after the scenario run.

Open `output/dashboard.html` and look first at:

- `No-op vs backfill` for the cache-reuse speedup.
- `Judge calls saved vs naive replay` for avoided replay work. The naive baseline is `sum(active trajectories per update)`.
- `Prompt & Code Provenance` for prompt hashes, reward logic versions, and prompt template versions by run.
- The `Change reward code` run, where reward calls appear without parser or judge calls.
- `Training Row Sample` for the OpenAI/TRL-shaped JSONL metadata that travels with each exported row.

## Manual Experiments

Start from a clean baseline:

```bash
uv run python main.py reset-demo
uv run cocoindex update main.py
uv run python main.py show
```

Add a trajectory. The simulated judge call count should increase by one.

```bash
uv run python main.py add-new-trajectory
uv run cocoindex update main.py
uv run python main.py show
```

Change policy and judge prompt. Parser/features stay cached, but judge/reward stages rerun because the prompt and thresholds changed. Both demo policies compare against the same `v17-prod` reference labels stored with each trajectory; the dashboard separately measures run-over-run flips.

```bash
uv run python main.py set-policy strict
uv run cocoindex update main.py
uv run python main.py show
```

Change Python reward code. Judge calls stay flat; reward decisions invalidate because `reward_logic.py` is declared as a function dependency.

```bash
uv run python main.py set-reward-logic tool_trace_bonus
uv run cocoindex update main.py
uv run python main.py show
```

Quarantine a trajectory. CocoIndex updates the catalog and removes any stale owned training-row file.

```bash
uv run python main.py quarantine traj_weather_002
uv run cocoindex update main.py
uv run python main.py show
```

## What To Edit

1. Edit `reward_policy.json` to change thresholds, penalties, or the simulated LLM judge prompt.
2. Edit `reward_logic.py` or switch variants with `uv run python main.py set-reward-logic tool_trace_bonus` to demonstrate code-aware invalidation.
3. Add, edit, delete, or quarantine files in `data/trajectories/`.

`run_verifier()` is intentionally a simulated LLM judge: it sleeps for 250 ms, hashes the prompt, and applies a deterministic rubric. Replace that function with a real model call when you want the same demo to show actual token latency and judge cost.

## Why CocoIndex Here

| Without a maintained view | With this example |
| --- | --- |
| Reward or judge changes trigger broad replay scripts: 40 simulated judge calls in this six-update sequence. | CocoIndex performs 14 actual judge calls; the no-op run records 0 stage calls. |
| Python reward-code edits usually risk stale judge outputs or broad replay. | Code-change run: 0 judge calls, 7 reward calls, and reward logic version changes from `code-v1-base` to `code-v2-tool-trace-bonus`. |
| Training exports drift from catalog state. | SQLite rows, JSONL exports, and reports are declared together. |
| Deleted or quarantined samples leave stale files behind. | Target ownership cleans removed training rows automatically. |
| Audit evidence lives in ad hoc logs. | Prompt hashes and reward-code versions persist in maintained rows; demo telemetry records exactly which memoized stages executed. |

The seed data is intentionally small enough to inspect by hand, but the expensive work is per-trajectory: each trajectory owns a stable component path, and bounded concurrent batches replay only changed components. Source discovery and the consolidated `training.jsonl` export still scan/assemble the active dataset; the per-row files and SQLite rows are the incrementally maintained artifacts to use at larger scale.
